一、FAISS 为什么不适合 aimindmap（三条论证）

理由一：量级不匹配——FAISS 是为百万~十亿级向量设计的

FAISS 的核心价值是近似最近邻（ANN）索引（IVF 倒排、HNSW 图、PQ 乘积量化），解决的是"向量太多、全量扫描太慢"的问题。它的典型应用场景是搜索引擎（数十亿文档向量）、推荐系统（数亿用户/物品向量）。

aimindmap 是个人笔记工具，单项目节点数在几千到几万量级。即使取上限 10 万节点、每个节点 768 维 float32 向量，全量线性扫描的计算量是 10万 × 768 = 7680 万次浮点运算——在现代 CPU 上几毫秒即可完成。这还没算上：实际查询时可以先按标签/项目/层级过滤，候选集往往只有几百到几千节点。

在这个量级下，FAISS 的 IVF/HNSW/PQ 索引纯属过度设计：索引构建需要聚类训练、增量更新复杂（HNSW 的删除是已知难题）、索引文件比原始向量还大。线性扫描反而更简单、更可靠、零维护。

理由二：违背"零运行时依赖"铁律——C++ 库在 Node/Electron 中的集成噩梦

aimindmap 的架构铁律（ARCHITECTURE.md §4 原则 4）明确规定："生产代码只用 Node 内置 + 本地 vendor；npm 依赖仅限 electron / jsmind / vitest(dev) / electron-builder(dev)"。

FAISS 是 C++ 库，在 Node/Electron 中集成只有两条路，两条都违背铁律：

  • Native 编译绑定（faiss-node 等）：需要 prebuild 二进制或 node-gyp 现场编译。问题链：(1) prebuild 二进制与 Electron ABI 版本不匹配时需要 rebuild；(2) asar 打包时 native 模块需要 unpack 处理；(3) Windows/Linux/macOS 三平台各需一套 prebuild；(4) FAISS 本身依赖 OpenBLAS/MKL，进一步增加 native 依赖链。这与 DSH 的 vendor 自包含运行包模式完全不同——DSH 是预打包的完整运行时（哈希锁定、原子切换），而 faiss-node 是需要编译集成的 native 模块。
  • 起 Python 子进程：用 Python 的 faiss-cpu 做检索，Node 端通过 stdio/HTTP 调用。这直接引入 Python 运行时依赖，违背零运行时依赖原则，且增加进程管理、版本兼容、打包分发的复杂度。

理由三：embedding 来源与 v2 自身矛盾——"FAISS 升 P1"和"本地模型降 P3"打架

FAISS 只做向量相似度搜索，它不生成 embedding。要使用 FAISS，必须先有一个 embedding 模型把节点文本转为向量。embedding 来源只有两个选择，而两个选择都与 v2 的结论矛盾：

  • 走云端 embedding API（如豆包/OpenAI embedding 接口）：那么语义检索的"本地增强"意义丧失——每次搜索都要调云端 API，与直接让 DSH AI 读树做语义定位功能重叠（DSH 本身就是云端大模型，读整棵树做语义判断比 embedding 相似度更精准）。而且增加了 API 调用成本和延迟。
  • 走本地小 embedding 模型（如 Qwen embedding、bge-small）：这又绕回了 v2 已经降级为 P3 的"本地模型"路线。v2 明确说本地模型"仅离线/隐私/批量场景按需启用"，那么依赖本地 embedding 的 FAISS 语义检索也应该是 P3，而不是 P1。

结论：v2 的"FAISS 提升 P1"与"本地模型降级 P3"是互相矛盾的两个结论。如果本地模型是 P3，那么依赖 embedding 的语义检索（无论用 FAISS 还是别的索引）都不可能是 P1。

FAISS 正式进入"不适合"清单

工具不适合的原因严重程度
FAISS ① 量级不匹配（几万节点线性扫描几毫秒，ANN 索引过度设计）；② 违背零运行时依赖铁律（C++ native 绑定或 Python 子进程）；③ embedding 来源自相矛盾（云端与 DSH 重叠，本地绕回 P3） 三条均成立，彻底剔除

二、语义检索能力的轻量替代方案（不依赖 FAISS）

剔除 FAISS 不等于否定"语义检索"这个能力。语义检索是能力，FAISS 只是实现之一。在个人笔记量级下，有三种更轻量的替代方案：

方案 A：纯 JS 线性余弦

  • 原理：节点 embedding 存 JSON（与项目 JSON 同目录或独立 .embeddings.json），查询时计算查询向量与所有节点向量的余弦相似度，取 top-k
  • 索引：无索引，全量线性扫描
  • 依赖：零新依赖（纯 JS 数组运算，Array.prototype.map/reduce 即可）
  • 性能：10 万节点 × 768 维 ≈ 几毫秒（现代 CPU）
  • 增量更新：节点 add/edit 时更新对应向量，O(1)
  • embedding 来源：仍需解决（见第四节）

方案 B：图传播

  • 原理：aimindmap 本身是知识图谱（节点树 + 跨项目链接 + assoc 关联实体）。从种子节点沿关联边（links/backlinks/assoc）扩散，按传播深度和边类型打分
  • 索引：无需向量，复用已有图结构
  • 依赖：零新依赖（复用 src/relations.js、src/links.js、src/assoc.js）
  • 性能：图遍历 O(节点数 × 平均度数)，极快
  • 增量更新：无需维护，图结构实时反映
  • embedding 来源：不需要 embedding！纯结构语义
  • 局限：只能找到"有显式关联"的节点，找不到"内容相似但未建链接"的节点

方案 C：复用 DSH 读树

  • 原理：不建任何索引。DSH AI 通过 read --brief 读取项目结构（省 40%+ token），用云端大模型直接做语义定位——"找跟 TCP 三次握手相关的笔记"时，大模型读节点标题+摘要即可判断相关性
  • 索引：无
  • 依赖：零（复用已有 DSH + CLI）
  • 性能：受 token 限制，大树需分批读或先按标签/层级过滤
  • 增量更新：无需维护
  • embedding 来源：不需要（大模型直接理解语义）
  • 局限：依赖云端、大树有 token 上限、每次搜索都要调 LLM

2.2 方案 B 的关键发现：图传播与现有能力高度重叠

方案 B（图传播）听起来很美好，但仔细对照 aimindmap 现有能力会发现：related <项目> <id> --depth 2 已经在做"从种子节点沿关联边扩散两跳"的事。它合并了出边+入边，标注了 out/in/both，本质就是图传播的一个实例。

方案 B 能增加的价值仅限于：(1) 扩散到 N 跳（N>2）；(2) 按边类型（link vs assoc vs 同父节点）加权打分；(3) 跨项目传播。这些是 related 命令的增量增强，不需要新框架，在现有 src/relations.js 上扩展即可。

结论：方案 B 不应作为独立的"语义检索"方案，而应作为 related 命令的增强选项（如 --depth N --weighted）来考虑。

三、语义检索是不是真空白？——先验证后建设

3.1 v2 的默认假设被推翻

v2 默认"语义检索是 DSH 覆盖不到的真空白"，因此直接把 FAISS 升为 P1。但这个假设未经实测验证。在个人笔记量级下，DSH 读整棵树 + 现有 related/backlinks/mentions 组合可能已经覆盖了大部分真实需求：

用户需求现有能力能否覆盖覆盖方式
"找跟这个节点相关的笔记" 已覆盖 related --depth 2（两跳图邻域）+ backlinks（反查）
"找提到某个概念但没建链接的笔记" 已覆盖 mentions --cross（未链接提及，跨项目）
"找包含关键词的笔记" 已覆盖 search（全文关键词检索）+ --tag 按标签
"找意思相近但用词不同的笔记"（真语义） 部分覆盖 DSH AI 读树 + 大模型语义判断，但受 token 限制且需调 LLM
"有内容但无人引用的孤立笔记" 已覆盖 orphans（关系审计）

3.2 "先验证后建设"门槛

v3 的核心方法论修正：语义检索建设前必须先过验证门槛，不得默认要建。

验证步骤（在投入任何语义索引开发之前）：

  1. 实测 DSH 读树定位能力：用真实项目（节点数 ≥1000），让 DSH AI 执行 10 个典型语义查询（如"找跟 OpenWrt 固件编译相关的笔记""找所有关于电源管理的节点"），记录：(a) 能否找到目标节点；(b) 消耗的 token 数；(c) 响应延迟；(d) 误报/漏报率。
  2. 实测 related --depth 2 + mentions 的覆盖率：对同样的 10 个查询，先用现有 related/mentions/search 组合，看能覆盖几个。
  3. 定义"语义检索不可替代"的场景：只有当 DSH 读树 + 现有命令组合反复失败的场景（如"大树下快速找到意思相近但完全无链接的节点"）出现 ≥3 次，才证明需要独立的语义索引。
  4. 通过门槛后再选方案：优先方案 A（纯 JS 线性余弦，零依赖），不考虑 FAISS。embedding 来源在第四节取舍。

3.3 验证门槛通过后的优先级

阶段条件动作

四、embedding 来源的诚实取舍

如果验证门槛通过、决定建设语义索引（方案 A），就必须面对 embedding 来源问题。v2 回避了这个问题，v3 给出诚实表述：

embedding 来源优点缺点与其他结论的关系
云端 embedding API（豆包/OpenAI） 质量高、零本地依赖、无需维护模型 每次搜索/索引更新都要调 API（有成本和延迟）；语义检索失去"本地增强"意义；与 DSH 读树做语义定位功能重叠（DSH 本身就是云端大模型，直接读树判断比 embedding 相似度更精准） 与"复用 DSH"路线重叠，性价比低
本地小 embedding 模型（bge-small / Qwen embedding，~100-500MB） 离线可用、零 API 成本、数据不出本机、检索延迟低（本地计算） 增加 ~100-500MB 体积；需要推理引擎（llama.cpp / ONNX Runtime）；小模型 embedding 质量有限；这又绕回了已降级为 P3 的"本地模型"路线 与"本地模型 P3"路线绑定，语义检索随本地模型一起降级
不做 embedding（方案 B/C） 零体积、零依赖、零维护 方案 B 只能找有显式关联的节点；方案 C 依赖云端且受 token 限制 与 v2/v3 的"复用 DSH + 零依赖"路线一致

诚实结论

在 aimindmap 当前的架构约束（零运行时依赖 + DSH 已内置 + 个人笔记量级）下，语义索引的性价比不高。

  • 走云端 embedding → 与 DSH 重叠，不如直接让 DSH 读树做语义定位。
  • 走本地 embedding → 与本地模型路线绑定，应随本地模型一起作为 P3 按需启用，而不是独立的 P1。
  • 不做 embedding → 用方案 B（related 增强）+ 方案 C（DSH 读树）覆盖大部分需求，零成本。

因此，语义检索（方案 A）的正确优先级是"待验证 + 有条件 P3"，而非 v2 的 P1。只有当验证门槛通过、且用户明确需要离线语义检索时，才随本地模型一起建设。

六、更新后的实施路线（v3）

阶段一：DSH 能力最大化 + 语义需求验证（1-2 周，零/低成本）

  1. DSH 能力边界文档（docs/DSH-CAPABILITIES.md）：列出 DSH 已能做的 AI 操作，防止重复建设。
  2. 优化指针 skill：增加常用 AI 操作模式示例。

  4. 实测 DSH MCP 客户端支持：确认是否支持外部 MCP，若不支持写 fetch skill。
  5. （可选）侧栏快捷指令按钮：一键打标签/摘要/抓网页存笔记。

产出：文档 + skill 优化 + 语义需求验证报告。零新运行时，零新 CLI 命令。

阶段二：related 命令增强（1 周，零新依赖）

  1. 如果验证期发现"图传播深度不够"是主要痛点，扩展 related --depth N --weighted：支持 N 跳扩散、按边类型（link/assoc/同父节点）加权打分。
  2. 复用 src/relations.js，零新依赖。MCP 透传。cli-integration.js 加断言。

产出：更强大的图关联检索。这是方案 B 的正确落地方式。

阶段三：按需建设（仅在验证门槛通过后，4-8 周）

  1. 语义检索（方案 A：纯 JS 线性余弦）：仅当阶段一验证发现 ≥3 个不可替代的语义检索场景时建设。embedding 来源随本地模型路线决定（云端则与 DSH 重叠不建议，本地则随 P3 一起）。
  2. 本地模型（含 embedding）：仅离线/隐私/批量场景。嵌入 llama.cpp + Qwen embedding 小模型作为可选 vendor 组件。语义检索的 embedding 由此提供。
  3. DeerFlow：仅长周期批量场景。第二 vendor 运行包。

产出：按需启用的扩展能力。如果验证门槛不通过，此阶段可无限期推迟。

八、风险与注意事项（v3 更新）

FAISS 剔除后的残留风险

  • 如果未来项目规模突破 10 万节点：纯 JS 线性扫描的性能可能下降。但届时可以再评估是否需要引入更高效的索引（不一定是 FAISS，也可以是纯 JS 的 HNSW 实现如 hnswlib-node——但那同样是 native 模块，需重新评估零依赖原则）。当前个人笔记量级下不构成问题。
  • embedding 质量的不确定性：如果验证门槛通过、决定建设方案 A，本地小 embedding 模型（bge-small 等）在中文笔记上的质量需要实测。可能出现"向量相似度不如关键词搜索准确"的情况。建议先在小数据集上对比 embedding 相似度 vs DSH 读树判断的准确率。

验证门槛的执行风险

  • 验证样本偏差：如果实测用的项目节点太少（<500）或领域太窄，结论可能不具代表性。建议用最大的真实项目（节点数 ≥1000）做验证。
  • "不可替代场景"的定义主观性：≥3 个不可替代场景是经验阈值，不是硬指标。如果用户明确表达"我就是要离线语义搜索"，可以跳过验证门槛直接进入阶段三（但仍不建议用 FAISS）。

继承自 v1/v2 的风险（不变）

  • DSH 绑定豆包云端模型，路线 A（复用 DSH）依赖云端可用。
  • 双 harness 并发写入风险（DeerFlow 场景）。
  • 指针 skill 的脆弱性（DSH AI 可能不按 skill 操作，需强调必须用 mm-cli）。
  • DSH 是否支持 MCP 客户端未实测确认。
