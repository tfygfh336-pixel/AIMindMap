### 静默闭环收口：L2 补第二条真机路径 + 取景确定性补「复位缩放/平移」（2026-09-26）

**一、L2 的真机判别力证明补齐第二条路径**（无需改代码，是**证明**而非改动）
上一轮的真机证明走的是"**取不到可见矩形**"分支（当时注入 `#main *{visibility:hidden}`，连容器自己都被隐藏）。
本轮改用**覆盖式遮罩**（在 `#main` 上盖一层不透明白色 `::after`）⇒ **容器自身不动、矩形照旧可测**，
判定只能走**统计量判空**那条路径。`[实测]`：

```
[PASS] 工具栏 :: rect={x:0,y:0,width:1424,height:46}  unique=566 range=69.0
[FAIL] 导图区 :: rect={x:0,y:46,width:1424,height:789} unique=1 range=0.0 variance=0.0   ← 矩形在、内容空白
==== 视觉断言（L2 关键区域）: 1/2 passed ====
```
还原后逐字节核对一致，复跑 **2/2 全绿、exit 0**。⇒ **两条路径（元素被隐藏 / 区域存在但内容空白）现在都有真机证据**，
而后者才是**真实渲染失败**的形态。

**二、取景确定性补「复位缩放/平移」**（这一条原来是缺口）
原 `prepareCapture()` 的注释写着"复位缩放/平移**未做**：需要先确认渲染层『还原视图』的 API 名，未验证前不猜"。
本轮查到并补上：API 名 = **`window.MMApp.resetView`**（`renderer/app.js` 导出、`renderer/app-view.js` 实现 =
100% 缩放 + 根节点居中 + 清空拖动造成的树偏移）。
**为什么它必须做**：冒烟断言里**确有**多处在改缩放/平移（`01-core.js` 滚轮缩放、`05-pan-lock.js` 十余处平移、
`07-data-safety.js` 中键平移），**多数自己调了 `app.resetView()`、但并非全部** ⇒ 补上之前这条只靠"恰好没人漏"侥幸成立。

**⚠️ 过程中我犯了一个错，且是被判据抓出来的**：第一版把"复位"放在**禁过渡之前**，
结果两次冒烟哈希**不再一致**（`unique` 462 vs 468）—— 因为 `resetView()` 会改变视图，若它伴随 CSS 过渡而过渡还没被禁掉，
截图就会**捕捉到动画中间帧**。**修法：先禁过渡，再做任何会改变视图的动作。**
（附带：修的过程中我在**模板字符串内部**的注释里写了反引号，提前终止了模板串 ⇒ 语法错。已修正。）

⇒ **可操作结论：改完 `main.js` 后的第一次冒烟可能给出不同截图 ⇒ 判定取景确定性时看第 2 次起的连续结果。**
截图的**稳定值确实变了**（差 6 个 unique 色），这是**预期**：现在取自**规范化视图**（100% + 根居中），
而不是"上一条断言留在哪就是哪"。

**R3 分层测试**：本轮**未新增单测**（仍 528 用例 / 31 文件）—— 改动落在 `main.js` 的冒烟取景路径上，

### `doc-facts.js` 可单测化：加 `require.main` 守卫 + 抽出纯函数 `parseClaims`（2026-09-26）

**修的是什么（不是格式问题）**：`scripts/doc-facts.js`（G6 文档真值门禁）原先在文件末尾**无条件执行 `main()`**，
于是 `require()` 它会**直接跑主流程** ⇒ **无法被单测引入** ⇒ 本工程门禁里，**它的判定逻辑长期没有单测**。

**而这个代价刚刚真实发生过**：2026-09-26 把"视觉断言数"加进真值时，它的断言正则**要求数字紧邻「断言」**，
而中文的自然写法是「**2 条视觉断言**」（类别词夹在数字与「断言」之间）⇒ **匹配不到** ⇒
把这个数写进任何 markdown 都**不进判定** —— **门禁在空转**。
发现它靠的是**一次手动的判别力证明**（注入一行错数、看门禁是否变红 ⇒ 结果 `exit 0` 没红），**不是单测**。
放宽正则后又**顺带抓到一处从未被门禁管过的既存缺陷**（`docs/ROADMAP.md` 里的冒烟断言数从 45 漂到 115）。

**做了什么**：
1. 抽出纯函数 **`parseClaims(line)`** —— 把"一行文本里的全部事实声明"的解析（四类计数 + 断言归类）
   从内层循环里独立出来，**无 IO、可单测**；`scan()` 改为调用它，**四处正则的匹配顺序与归类规则逐字保留**。
2. 加 **`require.main` 守卫** + `module.exports = { parseClaims, scan, trackedFiles, markdownFiles }`。
   `[实测]` `require` 耗时 **7189 ms → 12 ms**；而直接 `node scripts/doc-facts.js` 的行为**逐字不变**（exit 0、输出相同）。

**R3 分层测试**：单测 **515 → 528**（+13，`tests/doc-facts.test.js`；`tests/` 文件数 30 → 31）——
覆盖：**类别词夹在数字与「断言」之间**（那次空转的根因形态）· **类别词在数字之后**（`ROADMAP.md` 那句被漏管的老形态）·
旧写法仍识别 · CLI/集成两种措辞 · **一个类别词都没有 ⇒ 不判定**（宁可不测也不误报）· 标题行整行跳过 ·
一行内多类声明 · 数值类型 · 正文裸数字不误判 · `scan` 的**判别力**（真值设为不可能的值 ⇒ 必抓到，且标签限于四类）·
`scan` 对 `null` 真值不产条目（"采不到真值=红"由调用方负责）· **受管文档排除了 CHANGELOG 与归档族**（且确实扫到该扫的）。

**R5 改动即连带**：`docs/VERIFY.md` → **已重生成**（528 用例 / 31 文件）· `scripts/verify.js` 的 `STEPS`/预算 → **无影响** ·
`docs/ARCHITECTURE.md` §5 / `docs/CLI.md` / `cli/registry.js` → **无影响**（未新增文档与命令）·

### 静默验证闭环 阶段 4：AI 读图留痕（2026-09-26）

**为什么它是脚本而不是门禁**：L1/L2 是机器判定，而 L4 判的是**语义级异常**

1. **哈希由脚本从 `smoke-frame.json` 机械取，绝不由人手打**，并**校验当前 `smoke-shot.png` 的 sha256

#### ⚠️ 判别力证明**第一次没通过**，而它抓出的是一处**真实的空转**

按工程既定做法注入一次违规（在 `docs/AI-GUIDE.md` 写「本项目共 99 条视觉断言」，真值为 2）
⇒ `doc-facts --check` **exit 0**，**没有变红**。

根因：断言正则要求**数字紧邻「断言」**（`(\d+)\s*(?:条)?\s*断言`），
而中文的自然写法是「**2 条视觉断言**」—— 类别词夹在数字与「断言」之间 ⇒ **匹配不到**。
⇒ 也就是说：**按自然写法复述视觉断言数，G6 压根扫不到**；不做这步修正，
"视觉断言数进真值"就**只对生成物成立、对一切叙事文档是空转**。

**修法**：正则允许数字与「断言」之间夹一个类别词（视觉 / 冒烟 / 集成 / CLI），
并且**优先用这个内联类别词**归类，没有才回退到既有的"数字之前最近的类别词"启发式。
⇒ 重做注入 ⇒ **exit 1**，报文精确指到行：`docs/AI-GUIDE.md:192 [视觉断言数] 写的是 99，应为 2`；
撤销后逐字节还原（sha256 与注入前一致）。

#### 放宽正则**顺带暴露出一处既存缺陷**（此前从未被门禁管过）

`docs/ROADMAP.md` 里有一句「…导出契约不变，**45 冒烟断言**全通过）」——
类别词（冒烟）在数字**之后**、紧邻「断言」，**旧正则扫不到** ⇒ 该数字从 45 漂到 115 **无人察觉**。

它记的是一批**历史**改动，所以正确修法**不是**把数字改成 115（那会让它变成"现状声明"），
而是**去掉数字、保留语义**（"当时的冒烟断言全通过"）—— 与 ADR「易腐事实不手写」一致。

### 新增 `npm run dsh:ratio`：实测 DSH token 启发式的真实偏差（2026-09-26）

**问题**：DSH 的 token 估算是**硬编码启发式** —— `dsh-token-meter/lib/index.js:16` `const CHARS_PER_TOKEN = 4;`，
且配置面被**显式封死**（`:604-606` 对任何键都抛 `TokenMeterConfig: unknown key … (no settings are supported)`，
`static Config = z.object({})`）。官方自己承认「**CJK text and JSON schemas underprice badly at four characters per token**」
（同包 `README.md:64,148`）。而这个估计量**直接决定压缩何时触发**
（`dsh-compaction-basic/lib/index.js:899-900` 拿 `measure().totalTokens` 比 `floor(contextWindow × thresholdRatio)`）。
估算偏小 ⇒ 阈值在**真实用量早已超过**时才触发 ⇒ **压缩来得比设计意图晚**。

**改不了它，但能量出它偏多少**：DSH 把两个数**明文**落在会话投影缓存里 ——
`record.rows.contextPressure.val.pressureTokens`（provider 报的**真实** prompt 量）与同处的 `surfaceTokens`（启发式量）。
本工具**离线**（零 API 成本、可复现）算出比值分布。

**`[实测]` 结果**（`~/.dsh`，即当前 harness 的 home）：

| 项 | 值 |
|---|---|
| 会话投影文件 / 可算比值样本 | 249 / **231**（另 **18 个退化样本**已排除并计数） |
| 比值 min / p10 / **中位** / p90 / max | 0.995 / 1.021 / **1.287** / 1.577 / 4.197 |
| 均值（与中位差得远 ⇒ 长尾） | 1.335 |
| 比值 < 1（**启发式反而高估**） | 10 / 231 |
| ⇒ 启发式**中位**偏差 | **低估 28.7%** |

**三条刻意不做的事**（都是"看起来更漂亮但会骗人"的选项）：
1. **不给"万能倍数"**：比值跨度 0.995～4.197，随中文/JSON 占比变化 ⇒ 只给分布与中位，并显式写"请勿当成万能倍数"；
2. **不说"启发式总是低估"**：实测有 10/231 的样本比值 < 1 ⇒ 该表述本身是错的；
3. **不把样本当目标实例的实测**：目标实例（AI MindMap 内嵌侧边栏）**零会话 ⇒ 零样本**，
   工具对它**如实报"这是有效结论，不是偏差为 1"**，并明确禁止把另一实例的数字当成它的实测（跨实例推断）。

**执行中真实踩到并已修掉的三个坑**（每个都写进了单测作回归守卫）：

| # | 坑 | 后果 |
|---|---|---|
| ① | 字段路径是 **`record.rows.contextPressure.val`**，我最初按顶层 `contextPressure.val` 扫 | 得出"249 个文件、**0 个样本**"的**假结论** |
| ② | 存在 `pressureTokens: 0` 的**退化样本**（provider 报 0 而启发式 >0），实测 18 个 | 不排除会让 `min` 变成 **0.000**、把分布拉到无意义 |
| ③ | 内嵌实例目录名是 **`AI MindMap`**（"AI" 后一个空格、MindMap 一个词；码点 `65,73,32,77,…`），我此前写成 `AI Mind Map` | `existsSync` 为 **false** ⇒ 把**正确的 home 误报成"路径给错了"** |

**退出码契约（两条路径必须分开）**：`home 不存在` = **1**（路径给错，是错误）；
`home 存在但没有投影/没有样本` = **0**（那是**有效结论**）——
把两者混成一个分支，就会对内嵌实例给出误导性的"路径错了"提示（坑 ③ 正是这样暴露的）。

### 新增 `dsh-caps`：DSH 能力边界（读装配清单，不是读 README）（2026-09-26）

**问题**：`docs/EXTENSIONS.md` 的哲学是「**AI 就是扩展机制** —— 长尾需求由 AI 组合现有原子能力动态完成」，
但它成立的前提是**知道原子能力有哪些**。缺了这一步的后果是**两个方向的判断都可能错**，而两者都在本工程发生过：

- **以为不具备、其实有** → 白写一个新命令/装一个新插件。外部复核报告就是把 DSH 已具备的能力判为"不具备"（能力表 12 行错 4 行），成因是**取证来源是 README 而不是运行时装配**；
- **以为有、其实没挂载** → 把不存在的能力写进文档骗后人。

**做法：一个只读命令，从两个机械来源现算（不落生成物）**

| 来源 | 读什么 |
|------|--------|
| **装配文件** `*/cordis.patch.yml` 与 `presets/*/agent.cordis.yml` | 到底挂了什么（自动发现，不硬编码路径） |
| **磁盘包目录** `node_modules/@deepseek-ai/*` | 发行包里到底有什么（239 个包） |

⇒ 得到**三轴事实**（磁盘 × 挂了没 × disabled），并明确写出**四条最易误判的规则**：

1. host 平面里 `disabled: true` **≠ 不可用** —— agent preset 会把同一 id 重挂；
2. 装配文件里**没有** ≠ **不具备** —— 包可能就在磁盘上；
3. 磁盘上**有** ≠ 当前可用 —— 未挂载的包在当前 profile 里不生效；
4. **host bundle 是并列的、不是叠加的** —— `--profile X` 选其中一套；**在 web 平面看不到某能力，不等于不能做那件事**。

**执行中它修正了我自己的结论（这正是它该干的事）**：

### P0-2：整条验证链只跑一次 vitest（省 8.5 s，并消掉那个偶发红）（2026-09-25）

**问题（两件事，同一个根因）**：
1. 第 4 步 `npm test` 跑一次 vitest，第 8 步 `doc-facts` **为了数用例数又跑一次** ——

2. 上一条（P0-0）里 D 盘连跑 4 次有 **1 次 `G6` 红**，根因正是这第二次 vitest 偶发取不到真值

   那正是刚建立起来的可信度的反面。

**做法：第 4 步顺手产出用例数，交给第 8 步**

| 位置 | 改动 |
|------|------|
| `scripts/verify.js` | 第 4 步改为 `vitest run … --reporter=default --reporter=json --outputFile=.review/verify-tests.json`（**人看的输出不变**）；跑前**先删**该文件、跑后读回 `numTotalTests`，经环境变量 `AI_MINDMAP_UNIT_TESTS` 交给第 8 步；读不到就打印降级提示（第 8 步自己再跑） |

**为什么可以信这个交接（安全性论证）**：`verify.js` **先删掉上一次的结果文件**再跑 `npm test`，

**因此也不会有「拿旧值当新值」的假通过**。

### 验证链改为带**耗时预算**的 runner：让 77 秒守得住（2026-09-25）

**问题**：本工程把 `npm run verify` 从 **176 s 压到约 77 s**（集成断言由"每条断言起一个 Node
进程"改为进程内调用，省下 98 s）。但这份收益**没有任何东西守得住** —— 后来者以"多加一条断言"
"多挂一个脚本"的名义就能把它一点点涨回去，而**每次只涨一点点，没人会注意到**。
这与本工程反复修过的病同型：没做坏事，却也让坏事看不出发生。

**做法：把 `&&` 链换成 `scripts/verify.js`（带计时的 runner）**

| 改动 | 内容 |
|------|------|
| `scripts/verify.js` | **新增**：`STEPS` 声明每一步（门禁／命令／覆盖／**预算**），逐条执行并**打印耗时表**；超预算即红 |
| `package.json` | `verify` → `node scripts/verify.js`（不再是一串手抄的 `&&`） |
| `scripts/doc-facts.js` | `docs/VERIFY.md` 的验证链表**改由 `verify.js` 的 `STEPS` 渲染** —— 顺带消掉上一批我手写的那份副本（一份事实只写一处） |
| `tests/verify-budget.test.js` | **新增 11 用例** |
| `docs/VERIFY.md` | 重生成（表格新增「耗时预算」列） |

**两个设计要点（都写在脚本头部）**：
1. **`stdio: 'inherit'`，不用管道** —— 受限环境（企业 EDR／沙箱）禁止管道 stdio，
   用管道收集输出会让**整条链**假失败（`docs/VERIFY.md`「本机受限环境注意」记着这个坑）。
   inherit 还顺带让子步骤输出**实时**可见。
2. **预算是「止涨线」而不是性能目标** —— 取实测的 2–3 倍。刻意留足余量：CI 与本机负载差异大，
   紧贴实测值会变成随机红灯，而随机红灯的下场是被人无视、或直接把门禁删掉。

**预算表**（唯一定义在 `scripts/verify.js`）：

|---|---|---|---|---|
| 1 | G1 | 0.8 s | 10 s | 12× |
| 2 | G8 | 0.6 s | 10 s | 16× |
| 3 | G9 | 0.6 s | 10 s | 16× |
| 4 | G3 | 8.7 s | 60 s | 7× |
| 5 | G4 | 4.9 s | 30 s | 6× |
| 6 | G5 | ~51 s | 120 s | 2.4× |
| 7 | G2 | 0.6 s | 15 s | 25× |
| 8+9 | G6+G7 | ~7.3 s | 40 s | 5× |

**判别力用真实历史数据验证过**（不是构造的样例）：`G4` 的 30 s 预算**能抓住历史上真实的
102.1 s**；合计 150 s **能抓住历史上真实的 176.3 s**。两条都写进了单测。

**每次运行都打印耗时表** —— 这是本次的**主要产物**：以后不必再问"verify 为什么慢"，
表里直接写着（当前 `G5` 冒烟占全链约 66%，属 Electron 真实启动的固有成本）。

### 并发写入闸门：界面保存不再静默覆盖 AI 的写入（2026-09-25）

**问题（先更正我自己的误判）**：我原以为"外部改盘"完全没保护。**实测后更正**：项目**已经有**
一半保护 —— `main.js` 的 `fs.watch` 监听项目文件 → 渲染层在**无未保存改动时自动重读**
（AI 的编辑实时出现在导图上），**有脏改动时只提示不覆盖**（`scripts/smoke/11-dsh-sidebar.js` 两条断言覆盖）。

**但缺口恰好落在"已经脏了"那一半** —— 而且 `renderer/app-actions.js` 自己的提示语就写着：

> `⚠ 笔记已被外部（侧栏 AI）修改，但你有未保存的编辑 —— **保存将覆盖外部改动**`

**它知道冲突、却不拦保存。** 用户随后一点保存，渲染层那份**整树内存拷贝**就把 AI 刚写的内容覆盖掉 ——
静默丢失。这正是 `main.js` `project:save` 顶部注释记的两条实测路径中的第②条
（第①条"内存是子集时写回删掉其他笔记"曾实测 7 篇 → 5 篇）。原实现只对 `assoc` 字段打了补丁
（磁盘优先），**节点树没有** —— 本闸门补的就是它。

**做法：内容指纹 + 版本闸门，CLI 与 GUI 共用一套语义**

| 位置 | 改动 |
|------|------|
| `src/data-store.js` | `read()` 一并返回**内容指纹**（SHA-1 前 16 位）；`write(name, data, {expectVersion})` 在写入前比对，不符则**拒绝**并报出两侧版本号；新增 `versionOf` / `versionOfText` |
| `cli/core.js` | `read()` 记下版本，`write()` 带上它 ⇒ CLI 的"读与写之间别处写入过"由**静默丢失**变成**响亮失败** |
| `main.js` | `project:read` 记下渲染层读到的版本；`project:save` 在**validate 探针之前**比对（这种失败要快），不符则抛出可操作的错误；渲染层已有 `catch` 显示路径（`app-actions.js` 的 `save()`），**因此无需改渲染层** |
| `src/ui-state.js` | 提示语补上闸门语义（AI 的写入不再会被静默覆盖；代价是界面随后保存会被拒并要求重开） |
| `scripts/smoke/15-write-conflict.js` | **新增** 3 条冒烟断言（见下） |
| `scripts/smoke-assertions.js` | 硬编码 require 列表 → **自动发现**（见文末"顺带"） |

**为什么用内容哈希而不是 mtime / size**：mtime 粒度粗到同秒两次写分不开；size 遇到"原地改一个字段"
完全不变（单测里专门锁了这条：同长度内容替换后 size 不变、指纹必须变）。两者都会让闸门**静默失效**。

   连带后面两条断言一起红。

   记录里那一版」时才推进**。这条前置条件正是它安全的原因 —— 若别处早已写过更新的版本，
   **绝不推进**（否则真冲突会被掩盖）；读命令不改盘 ⇒ 自动不推进。

### 新增 `changelog` 命令：把 236 KB 的变更轨迹变成窄查询（2026-09-25）

**问题（实测）**：`CHANGELOG.md` 已长到 **2,288 行 / 235,890 B**（16 段 / 90 条目），
而「上个迭代改了什么」是**每轮都要问**的问题 —— 且它是本工程**唯一的历史入口**：
git 侧零提交，没有 `log` / `blame` / `bisect` 可替代。当前只能整读或盲 grep。

**关键设计决定：不做「生成索引文件」，做「窄查询命令」**

第一直觉是仿照 `docs/CLI.md` 做一个 `docs/CHANGELOG-TOC.md`（生成物 + G7 过期门禁）。
**否决了这个方案**：CHANGELOG **每次变更都要动**（R2 双文档同步），
若索引是生成文件且受门禁检查，就等于给**最频繁的那个动作**新增一道强制重生成步骤 ——
在我们正要消灭迭代成本的时候反过来加成本。

改为把索引做成**命令**：从正文**现算**，不落任何生成物。收益：

- **永不漂移**：正文是唯一真源，索引只是视图（符合「一份事实只写一处」）；
- **零额外步骤**：记变更条目不需要多做任何事；
- **可发现**：进 registry ⇒ 自动进 `--help` 与 `docs/CLI.md`，与 `search` / `mentions` / `orphans`
  同属"只读查询命令"这一既有范式。

| 文件 | 改动 |
|------|------|
| `src/changelog.js` | 新增 **`indexChangelog(text)`**（纯函数）：段/条目两级索引 + 1 起行号 + 行数 + **UTF-8 字节数** |
| `cli/commands/release.js` | 新增 `changelog(ctx)` 命令（**只读**）：索引模式 / `--grep` 检索 / `--full` 带正文 / `--limit n` / `--json` |
| `cli/registry.js` | 登记 `changelog`（命令数 43 → **44**） |
| `tests/changelog.test.js` | +**7 用例**（`indexChangelog`） |
| `scripts/cli-integration.js` | +**7 断言**（含一条"跑完 CHANGELOG 逐字节未变"的**只读**守卫） |
| `docs/ARCHITECTURE.md` §2.2 · `SKILL.md` · `README.md` | 同步（新命令是用户可见面） |
| `docs/CLI.md` · `docs/VERIFY.md` | 重生成（`docs-gen` / `facts:write`） |

**为什么索引里不写日期**：实测 90 个条目标题里 **22 个日期格式各异**
（`（v0.16.6，2026-09-24）`、`（2026-09-15 晚）`、甚至完全无日期），拿它当索引键必然漏。
日期只从**段标题**取（15 个版本段格式统一为 `- YYYY-MM-DD`）；条目只报行号、行数、字节数 ——
索引的职责是"告诉你东西在哪、有多大"，不是"复述内容"。

**实测收益**：`changelog` 索引输出 **125 行 / 10,421 B**，对比全文 **235,890 B** ⇒ **约 22.6× 缩减**；

### 集成断言改进程内调用：`cli-integration.js` **102 s → 4.8 s**（2026-09-25）

| `cli/main.js` | 拆出 `dispatch()`（选命令、建 ctx、**刻意不 await**），其上两个入口：`invoke()`（异步，原有）与 **`invokeSync()`（同步，新增）**；二者共享 `beginCapture` / `endCapture` / `fail` |
| `scripts/cli-integration.js` | **只换 `run()` 的函数体**（`spawnSync` → `invokeSync`），其余 **188 个 `run()` 调用点一字未动**；另加 4 条**真子进程对照**断言；`process.exit(...)` → `process.exitCode` |
| `cli/commands/*.js`（7 个） | **未改动** |
| `tests/cli-main.test.js` | 新增 `invokeSync` 契约 **5 用例** |
| `tests/cli-sync-invariant.test.js` | **新增**：静态守卫（见下） |

**为什么可以有「同步版」—— 以及它为什么必须是显式不变量**

`cli/commands/*.js` 全写成 `async function`，但**一处 `await` 都没有**，也没有 `.then()` /
`fs.promises` / `setTimeout`（沿 `require` 闭包 grep 为 0）。JS 里 async 函数体在遇到第一个
`await` 之前是**同步执行**的 ⇒ 这些命令实际同步完成，`cmd.fn()` 返回**已 resolve** 的 Promise。

⇒ 不必把 188 个调用点改成 `await`（那要动近 200 处，其中 93 处是 `JSON.parse(run(...).out)`
这类**嵌入形态**，机械替换必漏）。代价是引入一条**隐式不变量**，用**两道防线**把它变成可机械发现：

1. **运行时**：`invokeSync` 用 `util.inspect(p).includes('<pending>')` 判断命令是否真跑完
   （实测可区分 `Promise { 1 }` 与 `Promise { <pending> }`），仍是 pending 就**立刻抛错**，
   绝不返回一个没跑完的结果；
2. **静态**：`tests/cli-sync-invariant.test.js` 沿 require 闭包扫 `cli/commands/*` + `core.js`
   + `registry.js` 及其依赖，命中 `await` / `.then()` / `fs.promises` / `setTimeout` /
   `process.nextTick` 即红并报出**文件:行号**；它还先自证"扫到了东西"（断言闭包非空），
   避免退化成"永远通过"的假守卫。

**数量一致性（G6 要求）**：4 条对照断言**逐条展开写、不用 `for` 循环** ——
`scripts/doc-facts.js` 用 `/^\s*check\(/gm` **静态**统计，循环会把 4 条压成 1 个调用点，
导致 `docs/VERIFY.md`（141）与运行时打印（144）不一致。展开后两者都是 **144**。

**R3 分层测试**：

  （大输出）/ 两条失败路径的 **stdout 字节 + 退出码**；两条执行路径漂移即红；

### CLI 入口拆薄壳 + `invoke()`：为集成断言去掉「每条断言起一个进程」（2026-09-25）

**问题（实测）**：`scripts/cli-integration.js` 的 140 条断言**每条起一个 Node 进程**
（`spawnSync`）。逐段量过：**140 条 / 102 s ≈ 0.73 s/条**，而每条的真实校验逻辑只有几毫秒 ——
绝大部分是进程冷启动。对照：同一代码基用 `vitest --pool=threads` 跑 351 个用例只要 **5 s**
（差两个数量级）。它同时是 `docs/VERIFY.md`「本机受限环境注意」记的那条假失败来源：
管道 stdio 被禁的环境下，这 140 条会**全部假失败**。

**做法：入口拆成「薄壳 + 纯函数」，不改任何命令实现**

| 文件 | 改动 |
|------|------|
| `cli/main.js` | **新增**。导出 `invoke(argv) → {code, stdout, stderr}`；内含 `captureStreams()`（临时接管 stdout/stderr 写入）与 `run()`；**不调用 `process.exit`**；进出都隔离 `process.exitCode` |
| `cli/mm-cli.js` | 改为**薄壳**：`invoke(process.argv.slice(2))` → stdout/stderr 落地、code 写进 `process.exitCode`。usage 渲染随之下沉到 `main.js`（单一渲染点） |
| `cli/core.js` | **未改动** —— `PROJECTS_DIR` 语义（require 时由 `AI_MINDMAP_PROJECTS_DIR` 决定）保持不变，故 MCP / 主进程 / 冒烟沙箱的重定向行为不受影响 |
| `cli/commands/*.js`（8 个） | **未改动** —— 选择「拦截 stream」而不是「命令返回字符串」，正是为了不动这 8 个文件（输出散落在 `ctx.out` / `ctx.outJson` / `console.log` 多处） |

**为什么 `code` 要「读回 `process.exitCode`」而不是只看有没有抛错**：`validate` /
`validate-all` 是**报告型命令**，以「FAIL 行 + 自行置非 0」表达失败，**不抛异常**。
只看异常会把它们误判成成功。

**R3 分层测试**：新增 `tests/cli-main.test.js` **9 用例**（单测；**故意不起子进程** ——
不把管道 stdio 依赖引回 `npm test`）。守四条不变量：失败契约（code 1 + `error: ` 前缀）、
命令内 throw 被兜住、**`process.exitCode` 隔离**、**stream 在成功与异常两条路径后都被复原**。
`docs/VERIFY.md` 由 `npm run facts:write` 重生成（用例 351→**360**、文件 20→**21**）。

**等价性验证（R1：断言由实际执行产生）** —— 两层，都跑过、都通过：

  `projects/`，拿改造前的副本 `cli/_baseline-mm-cli.js` 与改造后的 `cli/mm-cli.js` 跑同一批参数，
  比较 **stdout 字节 / stderr 字节 / 退出码**。覆盖 usage、216 KB 大输出、报告型命令，
  以及四类失败路径（未知命令 / 不存在的 id / 缺参数）。

### 架构：服务驻留语义落地 + 「写前协调」改为可执行通道（v0.16.6，2026-09-24）

用户要求一次做三件事：① 让 `destroy()` 不再收割服务、运行锁记服务 pid；
② 加 `ui-state` 让侧栏 AI 真能读 dirty；③ 补文档 + 清测试残留。

#### ① 主界面退出不再收割 DSH 服务（README 承诺兑现）

- **问题（设计意图 vs 实现脱钩）**：README 承诺「重启/升级主界面时侧栏对话不中断，
  新主界面自动接管既有服务」，但 `destroy()` 在 `state.proc` 存在时直接
  `taskkill /T /F` —— **正常退出必然杀掉服务**，接管路径只在异常终止后才会走到。
  `scripts/dsh-resident-e2e.js` 证明的是 Node 层 detached 机制，没覆盖
  Electron 的 `will-quit → stopService` 这条真实路径（该脚本注释自称"与 main 同款配置"，
  实际 main 用 pipe、脚本用文件 fd，并不相同）。该脚本连同另外两个一次性探针
  （`dsh-detach-probe.js` / `dsh-resident-probe.js`）**已删除** —— 它们都是"手工跑一次看结果"的
  诊断件：没有断言、清理靠 best-effort，中断就漏下一个孤儿服务（实测本机残留 **9 个**
  监听端口的 vendor/dsh 服务进程，累计占内存）；同一实验现在由 `npm run dsh:resident`
  带断言 + `process.on('exit')` 兜底清理承担。
- **修复**：`destroy()` 分三种情形 —— 已就绪（running + url + servicePid）→ **驻留**
  （保留 `dsh-service.json`、锁留给服务、只断引用）；未就绪 → 照旧收割
  （半启动进程会占住运行锁，让下次既接管不了也孵化不了）；仅持锁（接管场景）→ 放锁。
- **stdio 从 pipe 改落文件**（`userData/dsh-service.log`）：主界面退出后 pipe 读端消失，
  服务再写 stdout 就 EPIPE —— 一个"退出主界面反而把侧栏弄崩"的隐性风险。改为文件 fd 后
  服务与孵化者彻底解耦；token URL 改由日志轮询抓取（`tailServiceLog`，300ms/次，
  从本轮启动的文件偏移开始读，不会误读上一轮服务的旧 URL）。
- **运行锁 pid 改指服务进程**（新增 `dshPackage.retargetRuntimeLock`）：锁原本记
  `process.pid` = 孵化者。驻留语义下孵化者先退出，锁就成了"陈旧锁"→
  `npm run dsh:maint -- import` 能在**活着的服务脚下**换运行包（服务跑旧包、新界面接管它）。
  改指后「锁活着」与「服务活着」同义，维护互斥重新成立（新增 4 条单测锁住）。
- **顺带修掉两个既有 bug**：
  · `stopService()` 原来只在 `state.proc` 存在时收割。接管实例（`proc=null`）走菜单
    「重启 DSH 服务」只会清掉 service-info、留下一个活着但没人认领的服务占住运行锁
    → **重启必然失败**。现按 `proc.pid ?? servicePid` 收割，并按 pid 精确清掉那条锁
    （新增 `dshPackage.clearRuntimeLockFor`）。驻留语义下"接管"是常态，这个 bug 会从偶发变必现。
  · `taskkill` 由异步 `spawn` 改**同步** `spawnSync`：异步子进程会随宿主 Job 一起被终止 ——
    "点完停止立刻退出应用"时收割根本没发生（`dsh:resident` 阶段 4 实测复现：宿主退出后
    服务仍在）。收割必须在返回前落地。
- **新增菜单「视图 → 停止 DSH 服务」**：驻留语义的必要正门（否则用户只能靠任务管理器）。

### 缺陷修复：框选筛选的分组键错误——跨主题节点未过滤（2026-09-24）

  "同一父节点"应当按**直接父节点**分组：wlan-01 的父是 wlan-book（深1），wlan-sta 的父
  是 wlan-02（深2），两组不同 → 取更浅的 wlan-01 组 → STA 被过滤。

### 规则：新增铁律 R5「改动即连带」——守"设计意图与实现一致"（2026-09-24）

**起因（用户指出的真实痛点）**：AI 迭代时经常**只验证"功能还能用"，不检查"GUI 呈现是否还符合设计"** ——
设计方法变了、实现跟着改了、测试照样绿，但人按原有习惯操作得到的效果已经不是设计意图。
排查确认这不是"AI 粗心"，而是**验证体系的结构性盲区**：G3/G4/G5 全是**行为级**验证
（按钮在、事件通、结果对），而"呈现层是否跟上设计"恰好落在所有门禁之外。

**这不是第一条此类规则，而是第四起同型事故后的归纳**（全部可考证）：
① 详情框改为「相关知识点」区后，图片区旧「🔗 跳转到」行未删 —— 还"能点"，点了没反应；
② `switchProject` 加同项目早退后，47 条同项目链接全部成死链；
③ 冒烟断言硬编码"关联成员数=2"，真实数据变多后测的是**错误前提**（本轮实测 71/72 才暴露）；
④ `mentions` 增补 `direction:'same'` 契约后，一条集成断言仍要求"每项都是 out|in"，自相矛盾却长期存在。
共同模式：**设计的对外呈现与实现脱钩后，没有任何机制强制呈现层跟着设计走**；GUI 恰是纯人工可感的一层，
AI 全绿收工、无人点界面，脱钩就静默存活。

**按元规则 M1 定级**：损害高 ✓ / 有真实事故 ✓ / 能写成具体动作 ✓ / **不可机械化 ✓**
（"某改动是否改变了设计意图"无法自动判定）→ 进铁律，不进门禁；且**刻意不做成"全自动检查"**——
硬做只能得到永远绿的假守护（G6 的教训：假守护比没有守护更糟）。

**R5 内容**：凡改变「某功能**如何被使用**」（数据形状、命令语义、交互模型、字段含义、默认值），
同一次改动里**列出**受影响的**使用者可见面**并逐个核对 —— GUI 交互（按钮/右键/菜单/快捷键/对话框/状态栏）、
冒烟与集成断言、`AI-GUIDE.md`/`README.md` 操作示例、详情框与关联笔记的渲染入口；
结论（**含"无影响"也必须写**）进 CHANGELOG。判据是"**人按原有习惯操作，得到的还是不是设计意图**"，不是"测试绿不绿"。

**同时修正 G5 的能力边界措辞**（RULES §2）：明确"G5 验证行为级可用性，验证不了设计意图与实现的一致性"
—— 仿 G1"抓损坏的结果、不抓违规的动作"的既有写法，**把门禁的盲区写在门禁旁边**。

**落点（按 M2 单源 + M3 动作现场）**：`docs/RULES.md`（R5 全文 + 来源 + G5 边界）、
`SKILL.md`（铁律 5，改代码者会看到）、`README.md` §九（摘要 4→5 条）、
`docs/AI-GUIDE.md` §4（维护规范表新增一行触发器）。
可选二期（另议）：把设计意图中**可机械判定的部分**逐步抽成断言（先例：`direction` 契约、`--raw` 契约字段、
"保存不丢 assoc"），让 R5 的负担随时间变小 —— 与"让门禁变大、让铁律变小"的既有方向一致。

**验证**：本文档改动**未跑任何验证**（用户明确指示：另一 agent 正在并行修改项目，
此刻跑 verify 会读到中间态产生假红、且可能与它的写盘竞争）。改动均为纯 markdown，不触代码；
下次代码迭代跑 `npm run verify` 时由 G6/G7 顺带核对本文件的数字与生成物。

### 新增「关联笔记」二级页面（N 元关联实体）（2026-09-16）

**功能是什么**：新增一类实体 **`assoc`（关联笔记）** —— 用来写"介绍二者/多者之间关联知识"的笔记。
它在界面里是一个**二级页面**：**只能从节点详情的「相关知识点」区进入**（它不是节点、不在树里、
命令面板也搜不到），**界面与节点详情完全一致**（复用同一个浮动详情框组件 → 拖动 / 四边四角改大小 /
📌 小锁 / 🖥 大锁 / 多框并存 / 随导图缩放全部相同），页内可**编辑标题与正文**。
数据形状（项目 JSON 顶层可选集合，与 `data` 平级）：`[{ id, title?, members:[{project,id}, …], note? }]`。

**设计依据（为什么不做成"挂在 `links` 上"）**：最初的选择是把笔记挂在 `links` 的边上，
实测后改为独立实体。**`links` 是逐条声明的有向边，图结构上完全能表达三角/两两互指** ——
它表达不了的是"把若干节点的关联当成**一个对象**"。挂在边上的三条硬伤均为**实测**（非推测）：

- **标题只能写成两端**：第三个成员在标题里消失；
- **重跑 `link` 会整个替换链接对象 → 笔记被抹掉**（实测 `note: false`，即笔记字段直接不见）；
- **`unlink` 会让笔记陪葬**。

独立实体另有身份与生命周期，三个问题都不存在；且成员是 **N 元（≥2）**、可从**任一成员**的
「相关知识点」区进入同一页（`assoc-list --node <id>` 亦然）。

**数据形状与兼容性**：`members` ≥2 且不可重复；成员可跨项目（`项目/节点id`）；
`note` 与节点 `detail` **同约定 —— 落盘是 HTML**，Markdown 只出现在命令行边界（`--note-md`，
命令内转 HTML）。**只增不改 / 向后兼容**：`assoc` 缺失 = 没有关联（合法），旧文件**不需要迁移**，
`formatVersion` 仍为 **2**；删空时 `assoc-remove` 把 `assoc` 键**整个去掉**（不留空数组噪音）。
`export-json`/`import-json` 同样携带 `assoc`（**漏掉它会让"无损备份"静默丢数据**，属本轮必须补的出口）。

**校验**：结构（id/members/title/note 类型、成员数、重复成员、重复 assoc id）+ **悬挂关联成员**
（成员指向的节点必须存在，**与悬挂链接同一处逻辑**）；`validate` / `validate-all` / 保存闸门都会报，
`assoc-add` 与 `assoc-edit --members` 在写入前也会逐个检查，故**造不出悬挂关联**。

**归属与"保存不丢 assoc"的机制**：`assoc` 的**主要作者是 AI/CLI**，界面**没有创建入口**（设计如此），
界面只读它、并编辑标题与正文（写操作走 CLI `assoc-edit`）。因为**节点树由渲染层拥有、assoc 由 CLI 拥有**，
本轮补了三处（否则都是**静默**丢数据）：

- `serializeTree` 带上 `state.assoc` —— 否则界面每次保存都会把它抹掉（同一类缺陷本工程犯过：
  `meta.author` 被硬编码成空串写回）；
- `project:save` 在渲染层没带 `assoc` 时**从磁盘现有文件取回**，不用空值覆盖 ——
  防止 AI 刚写的笔记被一次界面保存清掉；
- 读入口时用 `assoc-list --raw` 把**原始实体**同步进内存 —— `--raw` 只给契约字段
  （`id`/`title`/`members`/`note`），避免把 `effectiveTitle`/`hasNote`/成员 `topic` 等
  **视图派生字段**写进数据文件造成污染。

**删节点是两侧唯一的交叉点**：被删（子）树可能是某些关联的成员。不处理就留下**悬挂成员**
→ `validate` 判红 → `project:save` 是校验闸门 → **保存被拒**；而界面没有"改成员"的入口
（只能编辑标题与正文）→ 用户会被卡死。故两侧各给一条出路，见下面「命令与 MCP」与「校验」两条。

**命令与 MCP**：CLI 新增 5 条 —— `assoc-list <项目> [--node <id>] [--json] [--raw]` /
`assoc-add <项目> --members a,b,c [--title 标题] [--note html | --note-md markdown] [--id id]` /
`assoc-edit <项目> <assocId> [--title 标题] [--note html | --note-md markdown] [--clear-note] [--members a,b,c]` /
`assoc-remove <项目> <assocId>` /
`assoc-prune <项目> [--nodes a,b] [--dry-run]`（清理已不存在的成员，修好悬挂成员导致的校验红；
默认只剪**确认不存在**的成员，项目读不出来的成员只警告、不猜）。
同批把**删节点**这条路修通 —— 删节点是 assoc 与节点树唯一的交叉点，也是本项目**最容易把用户锁死**的地方：
被删（子）树可能是某些关联的成员，不处理就留下悬挂成员，而 `project:save` 与 CLI 的每次
`ctx.write` 都过 `validate` 闸门 → **被判红的项目此后所有写操作都被挡住**，界面又没有"改成员"入口。

- `remove <项目> <id> [--clean-assoc] [--clean-links]`：发现被删（子）树被**关联**或**链接**引用时
  **拒绝执行**（不是警告后照删）并给出两条路（`--clean-*` 同步剪引用，或先 prune 再删）；
- **界面**的删除同规约：先读一遍 assoc（`assoc-list --raw`）与同项目入边链接 → 弹确认列出影响面
  → 经 IPC `app:pre-delete-cleanup` 让 **CLI 在磁盘上**先剪干净（`links-prune` + `assoc-prune`）
  → 成功后才删节点。**清理失败就不删**，绝不留下"保存不了"的中间状态。

> **为什么清理必须走 CLI、而不能在渲染层内存里剪完指望保存一起写回**（实测踩过）：
> `project:save` 在载荷里没有 `assoc` 时会**从磁盘取回**（那是为了防止 AI 刚写的笔记被一次界面保存
> 抹掉），于是"我把 assoc 清空了"与"我没见过 assoc"在载荷上**无法区分** → 内存里剪掉的成员会
> **原地复活**、悬挂成员依旧存在、保存照样被拒。assoc 的作者是 CLI，写就只经 CLI。

**另修掉三个同类缺陷**（都是"闸门读的是磁盘旧态"或"没有清理路径"）：

1. **闸门慢一步**：`validateProject` 新增 `selfProject` 参数 —— **本项目**的链接/关联成员以
   **即将落盘的 data** 为准（原先读盘，会把"刚删掉的节点"算成还在，第一次保存放行、第二次才突然
   被判红，那时所有写命令都已被挡住）；跨项目成员仍读盘（磁盘是唯一真值）。
   主进程保存前校验的同目录临时文件也据此推断项目名，界面删节点后**第一次**保存就会被正确拦下。
2. **备份无法恢复**：`import-json` 同样传入 `selfProject`。备份里的链接/关联成员多半指向
   **这个项目自己**，而恢复时它在磁盘上恰恰不存在 —— 原先会把整份备份判成"悬挂链接"而拒绝导入
   （实测：删掉项目后导入它自己的备份直接失败，备份形同废纸）。真悬挂仍被拒。
3. **删链接没有任何修法**：新增 `links-prune <项目> [--nodes a,b] [--dry-run]`。链接可以指向
   **别的项目**，对方删掉节点后本项目的链接就悬空、本项目被锁死，而界面上没有"删链接"的入口 ——
   这条自救路原先根本不存在。默认只删**确认不存在**的目标；项目读不出来时只警告、不猜
   （"采不到真值 = 红"）。同项目入边链接在 `remove` 里由 `--clean-links` 同步清掉。

MCP 新增 6 个纯透传工具：`assoc_list` / `assoc_add` / `assoc_edit` / `assoc_remove` /
`assoc_prune` / `links_prune`，并给 `remove_node` 补上 `clean_assoc` / `clean_links` ——
否则 AI 通过 MCP 删节点后也会撞上同一堵墙且**无法自救**。

**C4. `export-html` 站点搜索把深层命中全藏掉（此前我的探针**测错了对象**，没发现）**
- 成因：搜索只对命中项**自身**的 `<li>` 切换 `hidden`，而条目是嵌套的 ——
  祖先一旦 `display:none`，整棵子树（含真正命中的深层节点）一起消失。
  comnet 上搜「交换机」的 6 个命中项**全在非顶层**，因此全都看不见。
- 修复：保留集改为**自底向上传播**（自身或任一后代命中则保留），并在搜索时展开折叠分支。
  该逻辑抽为 `searchKeep()` 并把**源码注入**页面，保证单测覆盖的就是页面跑的那份实现。

**C5. `markdown` 超过 6 层静默丢节点**
- 成因：heading 用 `'#'.repeat(level)`，第 7 层生成 `#######`，而导入的正则只认 1–6 →
  该节点降级成父节点 detail 里的一行字面井号。实测 8 层树往返后只剩 L1..L6。
- 修复：层级夹取到 6 + 用缩进保留深度；8 层往返不再丢节点。

**C6. `schema` 的 `errors` 是模块级共享数组**
- 复现：`v1 = validateProject(好数据)` 后再校验坏数据 → `v1.ok===true` 但 `v1.errors` 非空
  （自相矛盾，`v1.errors === v2.errors`）。任何"先收集再统一报告"的调用方都会读到被污染的数组。
- 附带：重复 id 按**祖先层数重复报**（3 层嵌套报 3 次）。
- 修复：改为每次校验用局部数组随结果返回；「重复 id / 环」检测拆成**整棵树一次遍历**
  （`checkIdsAndCycles`），不再逐层重复。

**C7. 渲染层：md 附件预览渲染成 `[object Object]`**
- 成因：IPC `app:read-file` 解析为 `{ok,text}`（失败也 resolve），渲染层却按字符串使用
  → `markdownToHtml({ok,text})` 产出 `"<p>[object Object]</p>"`，且 `.catch` 永不因读取失败触发。
- 修复：解构并判 `ok`（失败键名是 `err`），错误信息转义后显示。

**C8. 命令面板/搜索框里按 Backspace 会删除当前选中节点（破坏性）**
- 成因：`editor.js` 的全局键盘处理只把三个对话框算作"在输入中"，
  而 `Delete`/`Backspace` 绑定的是**删除整棵子树**。
- 修复：新增 `inTextInput()` 判定（含 `#palette-input`、`#search-box`、contentEditable）；
  输入框内只保留撤销/重做/保存。同时命令面板的快捷键改为 `stopPropagation`，
  避免一次 Esc 连带关掉审计面板/浮动详情。

#### D. 其它

- **D1 `export-html` 的 node id 未转义**（纵深防御）：id 虽受 schema 约束，但手工编辑过的
  项目 JSON 可含任意字符；裸拼会破坏属性/注入标签，且 `querySelector` 插值 id 会抛
  `DOMException`。已全部走 `esc()`，并改为扫描比较属性值而非拼接选择器。
