## 0. 为什么要有这份文件（且只有这一份）

历史上"铁律"写在 6 个文件里，并且**已经漂移**：`README.md` §九列 7 条、`SKILL.md` 列 6 条，
两份清单不一致 —— README 独有「单一真源」「数据改动走 CLI」，SKILL 独有「分层测试
（改核心加单测／加命令加断言／加渲染加断言）」。而**漂移掉的那条恰恰最要命**：
本次审计修出的 20 余处缺陷里，多数是"不变量无人断言"，正是「分层测试」想防的事。

这与本工程修过的「文档数字 6 份副本互相矛盾」是**同一种病**：同一事实多副本、无单源。
所以规则系统也照同一味药处理 —— **单源 + 机器校验 + 显式标注强制方式**。

## 1. 规则分级（决定一条规则该以什么形式存在）

| 层级 | 定义 | 存在形式 | 违反的后果 | 强制方式 |
|------|------|---------|-----------|---------|
| **门禁 Gate** | 可机械验证 | 脚本，挂在 `npm run verify` | **验证直接变红** | 自动，不需要记 |
| **铁律 Rule** | 不可机械验证 **且** 损害高、不可逆 | 本文件 §3（仅数条） | 靠自觉 —— **已显式标注** | 自觉 |
| **约定 Convention** | 不可机械验证 **且** 损害低 | §4 或相应设计文档 | 不一致，但可修复 | 自觉 |

> **核心推论：一条已被机械化的规则，应当退出铁律名单。**
> 铁律是"无法机械化的残差"。所以**铁律条数多不是严谨的信号，而是门禁缺失的信号**。
> 目标是：让门禁变大，让铁律变小。

## 2. 门禁（自动强制，不需要记住）

| ID | 门禁 | 防的损害 | 实现 | 挂载点 |
|----|------|---------|------|--------|
| **G1** | 编码完整性 | UTF-8 BOM、乱码、解码失败（**全损事故二的成因**） | `scripts/encoding-check.js` | verify 首步（快速失败） |
| **G2** | 数据校验 | 结构非法、重复 id、成环、悬挂链接 | `node cli/mm-cli.js validate-all` | verify |
| **G3** | 单元测试 | `src/` 共享核心回归 | `npm test`（vitest） | verify |
| **G4** | CLI 集成断言 | 全部 CLI 命令行为回归 | `scripts/cli-integration.js` | verify |
| **G5** | 冒烟断言 + **真实数据隔离** | 渲染层回归；测试污染真实笔记 | `scripts/smoke-assertions.js`（入口）+ `scripts/smoke/NN-*.js`（分域断言）+ `main.js` 的冒烟沙箱 | verify |
| **G6** | 文档数字与版本一致性 | 同一事实多副本漂移（命令数/用例数/断言数/版本号）；**体量/行数类易腐数字**（`N KB/MB`、三位数以上「N 行」而无版本锚或历史标记）；**高于发布版本的 `vX.Y.Z`**（分不清是笔误还是另一套命名空间 —— 接手演练实测出的交接面歧义） | `scripts/doc-facts.js --check`（+ `tests/doc-facts.test.js`） | verify |
| **G7** | 生成物未过期 | 改了 `registry.js` 忘跑 `docs-gen` → `CLI.md` 落后 | `doc-facts.js` 用同一渲染函数重算并逐字比对 | verify |
| **G8** | 文档体系完整性（**15 条判定**，分五类：**准入**（登记 / 家门 / 白名单 / 悬挂 / **层取值表**）· **一致性**（归档重复 / 契约字段覆盖 / 章节编号 / 登记表与元信息 / **CLI 稳定性表覆盖**）· **结构**（归档横幅 / 工作目录状态 / 导航可达）· **交接**（死指针）· **代码入档**；**逐条清单跑 `npm run check:docs -- --judgments` 现场取**，不在此逐条复制） | **表外文档、散落文档、工程根与顶层目录乱放**（文档冗余与"同一事实多副本"的入口）；**交接面死指针**（接手者白找一场）；**新代码文件没进架构文档**（接手者不知道它存在）；**归档没横幅**（grep 到旧稿会当成现状）；**工作目录没声明死活**（误删在飞工作／把陈旧分析当现状）；**受管文档从 SKILL.md 找不到**（第一屏不可达 = 等于没有这份文档）；**数据契约缺字段**（照着契约改就会漏 —— `meta.layout` 实测漏过一次）；**章节编号断号**（读者去找一个不存在的节）；**登记表与文档元信息不一致**（表是生成的，手改或忘了重生成都会漂）；**元信息的「层」不在取值表内**（声明了一个不存在的层 —— 值不在表内是**配置错误**不是文档错误：要么改文档，要么把新层加进取值表并同批改 `SKILL.md` B3）；**元信息块缺行**（`不该写`/`更新方式` 缺失时登记表会用默认值把它掩盖成"看起来合规"）；**受管文档读不出/不存在**（采不到真值＝红，静默跳过会被当成通过）；**CLI 稳定性表漏登记命令**（`docs/EXTENSIONS.md` §1.2 的三级表是"外部工具/AI 能依赖哪一级"的契约，漏登记的命令谁都不知道能不能依赖 —— `import-project` 与另外 11 条实测长期不在任何一级里） | `scripts/docs-registry-check.js`（+ `tests/docs-registry.test.js` 锁判别力；15 条判定各自做过注入验证。**条数由 G9 与本文件里的 ①…⑮ 标记机械对齐** —— 写死过就会漂） | verify 第 2 步（紧跟 G1，快速失败） |
| **G9** | 规则文件自洽（**6 条判定**） | **规则文件自己漂移**：声明条数与表格行数不符、表格被引用块/空行打断导致行掉出表格（渲染成纯文本）、引用了不存在的编号、实现列点名的脚本已不存在、其他文档对条数的转述不符、**门禁声明的判定条数与实现脚本的判定标记数不符（标记还可能重复；实现脚本的文案里也不得再写死条数）** —— 本文件是手写的唯一权威副本，却没有任何东西守它自己 | `scripts/rules-consistency.js`（+ `tests/rules-consistency.test.js` 锁住判别力） | verify 第 3 步（纯文本解析，毫秒级） |

> **G5 的能力边界（与 G1 同理，必须诚实标注）**：G5 验证的是**行为级可用性** ——
> 按钮还在、事件还通、结果正确。它**验证不了「设计意图是否仍与实现一致」**：
> 实现方式变了、旧呈现还"能工作"，G5 照样绿（已发生四起，见 §3 铁律 R5 的来源栏）。
> 这类损害由 **R5「改动即连带」** 承担 —— 那是人工判定的残差，不要指望门禁兜住它。
>
> （这段话原先是插在 G5 行与 G6 行之间的。**G9 上线时它被判为缺陷**：markdown 表格一被空行
> 打断即结束，于是 G6/G7/G8 三行**掉出表格、渲染成纯文本**，在权威规则文件里静默消失。
> 现移到表后 —— **要给某一行加旁注，写在这里，不要插进表格中间**。）

> **G9 的能力边界（诚实标注）**：它只查**自洽**（前后是否一致），查不了**内容对不对** ——
> 一条铁律是否真的"不可机械化"、一条门禁是否真的防住了它声称的损害，仍靠人判定。
> 它也不查 `CHANGELOG.md`（历史记录里出现已退役的编号是正常的，不是缺陷）。
> 另外它规定了**一个二级章节里只允许一张 ID 表**（否则无法区分"两张表"与"表格被打断"）。

> **G8 的能力边界（诚实标注）**：它**只查"文件有没有家、在不在登记表/白名单里"**，查不了
> "这份东西该不该存在""内容是否与别的文档重复" —— 那是 `ARCHITECTURE.md` §5 决策树
> 与元规则 M2 的残差，仍靠自觉。它把可机械化的那半（表外文档、散落位置、根目录乱放、悬挂登记）
> 变成了红。**它也管不到工程外**（如 `.user_skills/` 根目录的散落文件）：那一层只有
> `SKILL.md` 顶部「落盘规矩」这条约定，没有门禁 —— 边界必须写明。

**门禁的判别力必须被证明过**：新加门禁时要故意注入一次违规、确认它变红，再撤销
（本项目已对 G1、G6、G7、G8、G9 做过该验证）。否则可能得到一个"永远通过"的假守护。

**"真值算不出来"必须当失败处理，绝不能跳过再宣称通过**。G6 曾犯过这个错：
受限环境下 vitest 子进程起不来 → `unitTests = null` → 该条比对被跳过 →
末尾照样打印"用例数…均与真值一致"并以 0 退出。**那不是通过，是没校验却报通过**。
现行为：真值缺失即 `✗ 无法取得单测用例数真值，门禁不能自称"已校验"` 并 exit 1。
推广到任何门禁：**采不到真值 = 红**；"跳过"必须显式可见，不能伪装成"一致"。

**门禁的能力边界要写清楚**：G1 抓的是**损坏的结果**，不是**违规的动作** ——
只读地误用 `Get-Content`（不写盘）不会留下痕迹，G1 无法发现。诚实标注边界，
比让人误以为它万能更重要。

## 3. 铁律（无法机械化，因此必须记住 —— 共 6 条）

| ID | 铁律 | 防的损害 | 为什么不能机械化 | 来源 |
|----|------|---------|----------------|------|
| **R1** | **对行为的断言必须由「实际执行过」产生，而不是由「看起来应该这样」产生。** 写下"支持/可以/会/返回/省 token"之前先跑一次；跑不了就显式写「未验证」 | 文档与实现脱节，且可长期潜伏 | 语义是否正确无法自动判定 | `detail` 格式被 5 份文档写成 Markdown（实际 HTML，潜伏数月）、`--brief` 文档称省 token（实际是空操作）、版本号 4 处各写一份 |
| **R2** | **双文档同步**：每次功能/格式变更同时更新 `CHANGELOG.md`（`[Unreleased]` 段）与 `README.md` | 变更失忆、产品文档落后 | "写得够不够"无法机械判定 | 历史约定 |
| **R3** | **分层测试**：改 `src/` 核心 → 加单测；加/改 CLI 命令 → 加集成断言；加/改渲染功能 → 加冒烟断言 | 修复无回归保护，同类缺陷反复出现 | 无法判定"断言是否足够" | 本次审计：`clone` 丢字段、`get path` 错、监听器泄漏、冒烟写真实数据 —— **全都是因为没有断言守住不变量**；后续 `palette-rank` 的负分缺陷也是**只有单测抓到**（冒烟断言不够细） |
| **R3a** | **编辑笔记 ≠ 功能迭代**：笔记内容增删改（add/edit/link/assoc 等经 CLI 的操作）**只跑 `validate <项目>` 一次**，**禁止跑 `npm run verify`**；verify 全链只属于"改应用代码"。适用对象包括外部 skill 消费者与内嵌侧栏 AI（指针 skill 内容已写死此边界） | AI 编辑笔记被误导进全量测试（几分钟白等）；编辑流程过重导致"边聊边编辑"不可用 | "是否改了代码"无法机械判定 | v0.16.1 用户明确要求区分两条轨道（SKILL.md 铁律 3 有对照表） |
| **R4** | **测试一律 headless**（`npm run verify`）。禁止用鼠标键盘操作界面来测试 | 验证不可重复、不可自动化 | 取决于执行者行为 | 历史约定 |
| **R5** | **改动即连带**：凡改变「某功能**如何被使用**」的改动（数据形状、命令语义、交互模型、字段含义、默认值），必须在**同一次改动里**列出受它影响的**使用者可见面**并逐个核对 —— GUI 交互（按钮/右键/菜单/快捷键/对话框/状态栏提示）、冒烟与集成断言、`AI-GUIDE.md`/`README.md` 的操作示例、详情框与关联笔记的渲染入口；核对结论写入 CHANGELOG（**结论是"无影响"也要写**）。判据不是"测试是否还绿"，而是"**人按原有习惯操作，得到的还是不是设计意图中的效果**" | 设计变了、实现跟着变了、但**对外呈现**还停在旧设计 —— 功能照常"通过测试"，人用起来却已经不是设计意图；且无人坐在屏幕前点一下，脱钩静默长期存活 | "某改动是否改变了设计意图"无法机械判定；"呈现是否仍符合意图"更无法自动判定 | 四起同型事故：①详情框改「相关知识点」区后，图片区旧「🔗 跳转到」行未删（还"能点"，点了没反应）；②`switchProject` 加同项目早退后 47 条同项目链接成死链；③冒烟断言硬编码"关联成员数=2"，真实数据变多后测的是错误前提；④`mentions` 增补 `direction:'same'` 后一条集成断言仍要求"每项都是 out\|in"，自相矛盾却长期存在 |

> R1 是本次新增的，也是**其余全部缺陷的共同母体**：那 20 余处问题里，凡不是"缺断言"的，
> 都是"用推理代替了验证"。它同时能解释为什么我会违反自己写的规则却毫无察觉。

## 4. 约定与架构决策（低损害或一次性决策，**不是**铁律）

| 事项 | 性质 | 正确的家 |
|------|------|---------|
| **单一真源**：本目录即完整工程，不分离 skill 与副本，只维护本目录 | 一次性架构决策（用户已否决多目录/软链方案） | `docs/ARCHITECTURE.md` 决策记录 |
| **数据改动的写盘出口**：新增写盘路径一律复用 `src/data-store.js` 的 `writeFileAtomic` | 架构约束（格式合法性由 G2 兜底） | `docs/ARCHITECTURE.md` |
| **数据改动走 CLI**：不直接手改 `projects/*.json`（迁移脚本除外） | 架构约束（G2 只兜住"结果非法"，兜不住"绕过流程"） | `docs/ARCHITECTURE.md` + `docs/AI-GUIDE.md` |
| **读写文本文件的工具**：读用 `read` 工具，写用 `write`/`edit` 工具；不要用 shell 命令读写文本 | 低损害约定（**写入**造成的损坏已由 G1 兜住；**读取**误用只会看到乱码，不损坏文件） | `SKILL.md` 操作段 + `docs/AI-GUIDE.md` |
| **新增文档准入**：新建 `docs/*.md` 必须**同批登记**到 `docs/ARCHITECTURE.md` §5 表（层/作用/不该写/更新方式）；`docs/` 之外不得出现文档；一次性分析稿 → `docs/archive/` 或工程外 | **已机械化**（表外文档、散落位置、悬挂登记由 G8 直接判红）；"该不该建这份文档"仍是约定 | `docs/ARCHITECTURE.md` §5（决策树）；违反即门禁 **G8** 红 |
| 不移动目录、不批量写盘脚本、大改前先导出备份 | 事故派生禁令（不可机械化，损害高但**动作可具体描述**） | `docs/INCIDENTS.md`（已在那里，不重复） |
| 节点粒度、detail/caption 写法 | 内容风格 | `docs/AI-GUIDE.md` §3（笔记内容规范） |
| **体量/行数类数字不手写**：不在文档与代码注释里写「CHANGELOG 已 <N> KB」「主文件 <N> 行」这类**随迭代变化**的数字 | **已机械化**（与 ADR「易腐事实不手写」同源）：受管文档里出现 `N KB/MB` 或三位数以上「N 行」而无版本锚 / 历史标记即判红；要当前值就**当场取**（`node cli/mm-cli.js changelog` / `node scripts/doc-facts.js`） | **G6**（`doc-facts --check` 的「体量/行数」一类）；放行条件 = 同行带 `vX.Y.Z`、或「快照」/「原记」/「当时」/「曾」 |
| **门禁的"判定列举"**：门禁行若**声明条数**，条数必须与实现脚本的判定标记机械对齐（**G9 判定⑥**）；若**逐条列举**判定，则列举必须与标记**一一对应** —— 做不到就**别逐条列**，改用"分类 + 现场取清单"（`npm run check:docs -- --judgments`） | 约定（列举是散文，解析起来脆弱；两条实测：同一条数先在四处有四种说法，改为机械对齐后又出现"声明 13 而只列 12"） | 条数部分由 **G9** 强制；列举部分靠本约定（**宁可少列，不要列错**） |
| **多会话并发写入**：本工程**同时会有多个 AI 会话在改**（实测被回退过两次：导航分组、CHANGELOG 段）。约定：**改动前先重读文件**（过期快照的编辑会被工具拒绝 —— 那是保护，不是故障）；发现自己的改动被覆盖时**不要反复重写**，先把现状读回来再决定；跑完 verify **复核自己的改动还在不在** | 低损害约定（可发现、可重做；数据层已有"并发写入即版本闸门"ADR，但**文档层没有版本可依**） | `verify` 与 `npm run check:docs` 每次打印「最近 N 分钟内有改动的受管文件」作为**告知**（不判红）；判定为"约定 + 检测"而非门禁 —— 锁在 AI 场景下会死锁/误杀（M1 判定） |
| **文档写作**：见 `docs/ARCHITECTURE.md` §5.0 五条（可执行/可验证/是"为什么" · 不写易腐数字 · 一份事实只写一处 · 报错即教程 · 状态措辞带锚） | 约定（写作方式不可机械化；但门禁能抓到漏网的结果） | `docs/ARCHITECTURE.md` §5.0；其中"易腐数字"已由 **G6** 兜底，"状态措辞带锚"是**人工残差**（G6 抓不到 `开发中` 这类标注） |

## 5. 元规则（管规则本身）

| ID | 元规则 |
|----|--------|
| **M1 准入** | 新增规则必须**同时**满足：(a) 有真实事故或已复现缺陷为据；(b) 不可机械化；(c) 损害高且不可逆；(d) 能写成具体动作。**不满足 (b) → 做门禁；不满足 (c) → 做约定；不满足 (a) → 不写。** |
| **M2 单源** | 规则只在**本文件**增删改。其他文档只放"执行该动作时当场需要"的条目 + 指向本文件的指针。 |
| **M3 动作现场** | 与具体动作绑定的规则，必须出现在**执行该动作时会看到的文档**里（如 `SKILL.md` 的操作段），不能只躺在规则清单里 —— 规则在计划期被读到、在动作期失效，等于没有。 |
| **M4 退役** | 规则一旦被机械化，就从铁律**降级为门禁**，并在本文件标注「已由 Gx 覆盖」。 |

**改规则的流程**：按 M1 判定层级 → 在本文件登记（含"来源"一栏，空着不许进）→
若是门禁则实现脚本 + 证明判别力 + 挂进 verify → 按 M3 在动作现场留条目与指针。
